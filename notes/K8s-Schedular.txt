### Taint & Tolarations
    = = = = = = = = = =
Suppose we do not wanted to put all PODs in the particular Node but there are few will allow to launch in that particular
Node call Taint and Tolarations. Taint means we are restricting and Tolarations means we are applying tolarations to 
specific Pods who can launch/Schedule in the Node (which labeled as taint).

Syntax:
> kubectl taint nodes node-name key=value:taint-effect

What happened to PODs who DO NOT TOLARATE the Taint?

there are 3 effects : NoSchedule | PferefNoSchedule | NoExecution

Ex:
> kubectl taint nodes node1 app=blue:NoSchedule

Tolarations:

defination adding to POD -

----
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod

spec:
  containers:
    - name: nginx-container
      images: nginx
  tolarations:
    - key: "app"
      operator: "Equal"
      value: "blue"
      effect: "NoSchedule"
----

There are 3 kinds of taint-effects:

* NoSchedule  -> POD will not be scheduled on the Node 
* PreferNoSchedule -> Prefer not to schedule but no gurentee
* NoExecution -> New POD will not scheduled on the Node, exiting node if any will be evicted if they do not tolarate the taint.


# compare the below command
> kubectl taint nodes node1 app=blue:NoSchedule

### Resource Requests (Limit): (How to allocate resources for PODs)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Example:
----
apiVersion: v1
kind: Pod
metadata:
  name: myapppod
spec:  
  containers:
    - name: data-processor
      image: data-processor
  ports:
    - containerPort: 8080

  resources:
    requests:
      memory: "1Gi"
      cpu: 1
----

By default K8s provide 512 Gi and 1 vCPU to container, if you wanted to increase use the followings:

----
apiVersion: v1
kind: Pod
metadata:
  name: myapppod
spec:  
  containers:
    - name: data-processor
      image: data-processor
  ports:
    - containerPort: 8080

  resources:
    requests:
      memory: "1Gi"
      cpu: 1
    limits:
      memory: "2Gi"
      cpu: 2
----

Exceeds limits: if CPU consumtion exceeds the limits then K8s try throttle CPUs but if memory consumption exceeds the limits
then PODs will be terminated.


Note on default resource requirements and limits
In the previous lecture, I said - "When a pod is created the containers are assigned a default CPU request of .5 and memory of 256Mi". For the POD to pick up those defaults you must have first set those as default values for request and limit by creating a LimitRange in that namespace.

apiVersion: v1
kind: LimitRange
metadata:
  name: mem-limit-range
spec:
  limits:
  - default:
      memory: 512Mi
    defaultRequest:
      memory: 256Mi
    type: Container
https://kubernetes.io/docs/tasks/administer-cluster/manage-resources/memory-default-namespace/

apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-limit-range
spec:
  limits:
  - default:
      cpu: 1
    defaultRequest:
      cpu: 0.5
    type: Container
https://kubernetes.io/docs/tasks/administer-cluster/manage-resources/cpu-default-namespace/

### Edit a POD
~~~~~~~~~~~~~~

Remember, you CANNOT edit specifications of an existing POD other than the below.

>> spec.containers[*].image

>> spec.initContainers[*].image

>> spec.activeDeadlineSeconds

>> spec.tolerations

For example you cannot edit the environment variables, service accounts, 
resource limits (all of which we will discuss later) of a running pod. 
But if you really want to, you have 2 options:

1. Run the kubectl edit pod <pod name> command.  
This will open the pod specification in an editor (vi editor). 
Then edit the required properties. When you try to save it, you will be denied. 
This is because you are attempting to edit a field on the pod that is not editable.

A copy of the file with your changes is saved in a temporary location as shown above.
You can then delete the existing pod by running the command:

> kubectl delete pod webapp

Then create a new pod with your changes using the temporary file

> kubectl create -f /tmp/kubectl-edit-ccvrq.yaml

2. The second option is to extract the pod definition in YAML format to a file using the command

> kubectl get pod webapp -o yaml > my-new-pod.yaml

Then make the changes to the exported file using an editor (vi editor). Save the changes

> vi my-new-pod.yaml

Then delete the existing pod

> kubectl delete pod webapp

Then create a new pod with the edited file

> kubectl create -f my-new-pod.yaml

Edit Deployments
With Deployments you can easily edit any field/property of the POD template. 
Since the pod template is a child of the deployment specification,  
with every change the deployment will automatically delete and create a new pod with the new changes. 
So if you are asked to edit a property of a POD part of a deployment 
you may do that simply by running the command.

> kubectl edit deployment my-deployment

### Admission Controller :
--------------------------

* Admission controllers provide advanced security and operational controls beyond basic 
  authentication and authorization in Kubernetes.

* They can validate, modify, or reject API requests before objects are persisted in the cluster.

* Built-in admission controllers include features like always pulling images, default storage 
  class assignment, and namespace existence validation.

* Admission controllers can be enabled or disabled via API server flags and can automate tasks 
  such as namespace creation.

Let's look at another type of admission controller plugin named the DefaultStorageClass plugin. 
This plugin is enabled by default. For example, when you submit a request to create a 
PersistentVolumeClaim (PVC), the request goes through authentication, authorization, 
and finally the Admission Controller.

The DefaultStorageClass Admission Controller watches for a request to create a PVC and 
checks if it has a storage class specified. If not, which is true in our case, 
it modifies your request to add the DefaultStorageClass to it. 
This could be whatever storage class is configured as the DefaultStorageClass in your cluster.

So when the PVC is created and you inspect it, you will see that a StorageClass default is added to it 
even though you had not specified it during creation.

This type of admission controller is known as a mutating admission controller. 
It can change or mutate the object itself before it is created.

Types of Admission Controllers:
--------------------------------
In Short:
To summarize, there are two types of admission controllers:

  Mutating admission controllers: These can change the request.

  Validating admission controllers: These validate the request and allow or deny it.
 
  There may also be admission controllers that can do both: mutate a request as well as validate it.

In the above steps, you have set up and deployed a demo webhook with the following behaviors:

* Denies all requests for pods to run as root in a container if no securityContext is provided.
* Defaults: If runAsNonRoot is not set, the webhook automatically adds runAsNonRoot: true and sets the user ID to 1234.
* Explicit root access: The webhook allows containers to run as root only if you explicitly set runAsNonRoot: false in the pod's securityContext.
